## 1. 改动详单（改前）

### C1 用 XNYS 日历算美股成熟时间
- **现状**：`app/service.py::_equity_maturity` 手写"跳周六日 + 9:30–16:00"。实测：
  - 半日市 cutoff=2026-11-27 12:00 ET +390 交易分钟 → 现返回 `11-30 12:00`，正确应为 `11-30 15:00`（差 3 小时）。
  - 感恩节 cutoff=2026-11-26 12:00 ET +390 → 现返回 `11-27 12:00`（把休市日 4 小时当交易日）。
- **计划**：`app/trading_calendar.py` 新增 `maturity_after_trading_minutes(start, minutes)`：按分钟推进，仅用 `XNYS.is_trading_minute` 计数；不在交易时段时用 `minute_to_session(direction="next")` 直接跳到下一个开市，避免长循环。`service._equity_maturity` 改为委托该函数，返回 UTC。
- **口径**：$(cutoff, t]$ 内的完整交易分钟数达到 N；分钟边界对齐。加密路径（`CRYPTO_ELAPSED_UTC_V1`）完全不动。
- **风险**：历史 PENDING 行的 `matures_at` 仍是旧值（不重写，保持"已冻结记录不改"）；新规则只影响新记录。
- **验证**：新增 `tests/test_equity_maturity.py`（正常周五、半日市、感恩节、周末、结算日必须落在真实 session 上）。

### C2 存储完整性对账脚本
- **现状**：`data/snapshots/` 189 份 vs `snapshots` 表 57 行，无任何对账；快照哈希写入后再未复核。
- **计划**：新增 `scripts/verify_store_integrity.py`：
  1. 快照文件 ↔ `snapshots` 表：孤儿文件、缺文件行；
  2. 逐条复核 `snapshot_sha256`（canonical JSON + 该字段置零，与创建时同算法），不一致只报告不修改；
  3. 引用完整性：analyses/tasks/outcomes/scenario_outcomes → snapshots/analyses；
  4. 输出 JSON（默认 `reports/store-integrity-<日期>.json`）+ 终端摘要；有问题时退出码非 0；
  5. `--quarantine-orphans` 才移动孤儿文件到 `data/orphaned-snapshots/`（移动而非删除，可逆）；默认只读。
- **风险**：legacy 行可能因 schema 演进报哈希不符 → 报告中区分 `hash_mismatch` 与 `file_orphan`，并在结论里标注"可能是历史 schema 版本"。
- **验证**：`tests/test_store_integrity.py` 用临时目录构造"孤儿文件 / 缺文件 / 哈希不符 / 引用缺失"四种场景；再在真实库上只读跑一次并把报告路径写进本日志。

### C3 演示提供者名显式化

### C5 僵死任务回收（fail-closed）
- **现状**：任务由 FastAPI BackgroundTasks 执行；进程被杀后记录永久停留 QUEUED/RUNNING。
- **计划**：`storage.list_tasks_by_status()` + `service.recover_interrupted_tasks()`：启动时把 QUEUED/RUNNING 标为 `FAILED_INTERNAL`，`ProblemDetail.detail` 说明"服务重启前未完成；按本地策略不自动重试、不调用模型"，并写 `task_recovered_after_restart` 审计事件；在 `lifespan` 启动阶段调用一次。
- **风险**：正在运行的另一进程任务会被误判 → 本项目为单用户单进程部署（localhost 边界 + 文件锁），可接受；且绝不自动重跑，不会产生模型费用。
- **验证**：新增测试（QUEUED/RUNNING → FAILED_INTERNAL；SUCCEEDED/FAILED_* 不动；不新增 analyses 行）。

### C6 两处小健壮性
- `create_snapshot`：`cutoff = request.cutoff_at or (now(UTC) if live else fixture 末柱收盘)`，去掉 `max(..., now)` 这种"live 也依赖 fixture 数据"的隐式写法；fixture 行为不变。
- `get_bars` 读取 `cache/history-progress/*.json`：解析失败（不存在/坏 JSON/校验失败）时降级为按质量摘要推导状态，而不是抛 500；失败记审计。

### C7 测试环境假设

### 3.3 过程中修正了我自己的一个错误结论

第一版对账脚本用"模型 round-trip 后重算哈希"，得到 16 条 `hash_mismatch`。改用**按存储原文重算**（canonical JSON + 哈希字段置零，不经过 Pydantic）后：

- 57/57 全部**通过**哈希校验（其中 51 条在 32 MB 上限内，6 条被保护性跳过）；
- 原因：`model_validate_json` + `model_dump` 会把后续版本新增的字段补成默认值，导致 dump 与写入时不同 → 那 16 条是**我方法错误造成的假警报**，不是数据被篡改。

因此 C2 的最终实现采用原文校验（对 legacy 行同样有效），并新增测试断言脚本哈希与 `app.storage.sha256_json` 一致。

  - **C 的 100% 不是预测力**：21 条里有 20 条在冻结时价格**已经**位于 SMA200 下方 2%–19.6%，

  - 真正有信息量的是**风险分解**：A 主判断有 **18%** 后续转 C（止损位就在脚下）；B 主判断只有 **10%** 转 C；
    每个冻结日的命中数在 1/8 到 8/8 之间剧烈波动（制度依赖），总命中率 58/96 不具备稳定外推意义。
  - 因此上一轮"8 条 A 里 5 条走成 B"的小样本说法，在大样本下应修正为：**A 是三类里最弱的主判断，
    B 更稳（转破位概率最低），C 只是描述"已经破了"**。
